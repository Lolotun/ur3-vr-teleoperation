# Позиционная телеоперация через ur_rtde

Режим ветки `ur_rtde`. Старые `servo` (виртуальный) и `up` / `wifi-speedl` сохранены.
Кинематика и обработка сингулярностей выполняются в MoveIt Servo на ПК.
Разбор измерений, anti-windup и численные примеры: [анализ изменений управления](rtde-antiwindup-analysis.md).
`ur_rtde_bridge` интегрирует ограниченные суставные скорости Servo в непрерывную
позиционную команду для `ur_rtde.servoJ`, контролируя её отставание от actual Q. Режим использует ROS 2 Humble и обычный UR3 (CB3).

```text
Unity ControllerPosePublisher: pose + Trigger heartbeat (30 Гц)
    → relative_pose_controller → /teleop/target_pose + /teleop/active (30 Гц)
    → pose_tracking_controller → /teleop/servo/twist + /teleop/servo/active (125 Гц)
    → MoveIt Servo → /teleop/servo/joint_trajectory (125 Гц)
    → ur_rtde_bridge: интегратор суставных скоростей → servoJ (125 Гц)
UR RTDE Receive → /teleop/tcp_actual + /joint_states (до 125 Гц, только свежие отсчёты)
Статусы: /teleop/pose_status, /teleop/tracking_status,
         /teleop/servo/status (Int8), /teleop/rtde_status
```

При превышении допустимого рассогласования суставов bridge останавливает
исполнение, сбрасывает интегратор и публикует
`COMMAND_REJECTED_RELEASE_TO_REARM: ...`. В диагностике указаны сустав с
наибольшим отклонением, `actual`, `command`, знаковая `delta` и `limit` в радианах.
Чтение RTDE и публикация TCP/суставов продолжаются. Для нового включения нужно
отпустить и снова нажать clutch; удержание кнопки не возобновляет движение.
При `RuntimeError` исполнения (включая отказ `servoJ`) чтение RTDE тоже
сохраняется, но статус `EXECUTION_FAULT_RESTART_REQUIRED` запрещает дальнейшие
команды до перезапуска backend. Отпускание clutch этот отказ не сбрасывает.
Лог содержит отправленную команду и снимок runtime/safety/robot mode,
speed scaling и фактических скоростей. Перезапуск программы робота автоматически
не выполняется. Ошибки самого Receive и операций вне шага исполнения по-прежнему
завершают поток со статусом `FAULT`.

## Ограничение накопления и защитная остановка Servo

Перед интеграцией скоростей применяется anti-windup. Отрыв считается для каждого
сустава как `q_cmd - q_actual`; при росте модуля отрыва приращения всего вектора
масштабируются одним коэффициентом, сохраняя направление суставной команды.
От `RTDE_LEAD_SOFT_START=0.06` до `RTDE_LEAD_SOFT_LIMIT=0.10` рад коэффициент
плавно падает от 1 до 0. Дополнительная проверка ограничивает один шаг, чтобы
не перескочить рабочий предел. Саму позицию команды не обрезаем скачком.
Приращения, уменьшающие отрыв, сами по себе не вызывают замедления; глобальный
коэффициент всё ещё может ограничиваться другим суставом. Робот может догнать
ограниченную цель и продолжить движение без отказа. При смещении actual извне
отрыв может превысить мягкий предел: разрешается его уменьшение, а аварийная
защита `RTDE_MAX_JOINT_TRACKING_ERROR=0.15` остаётся независимой.

Параметры должны удовлетворять `0 < soft_start < soft_limit < hard_limit`.
Они доступны в `.env`/Compose и launch как `lead_soft_start`, `lead_soft_limit`.
`anti_windup_scale` в телеметрии и сводке показывает вмешательство ограничителя.
Он может уменьшать достижимую скорость при отставании робота; задержку самого
servoJ это не устраняет. Удержание обычной нулевой скорости остаётся штатным.

Статусы Servo 2 (сингулярность), 4 (коллизия), 5 (граница сустава) отдельно
защёлкивают `SERVO_HALT_RELEASE_TO_REARM`. В ближайшем цикле RTDE вызывается
`servoStop`, интегратор очищается, новые servoJ не отправляются. TCP и суставы
продолжают публиковаться. `relative_pose_controller` сбрасывает старую привязку
VR, поэтому прежняя далёкая цель TCP не восстанавливается после нового включения.
Для повторного включения нужны физическое отпускание `/vr/right_hand/active`,
свежий неостанавливающий статус Servo и новое включение upstream active.
Автоматическое падение `/teleop/servo/active` без отпускания оператора недостаточно.
Пока робот остаётся в сингулярности, декартово управление может оставаться
заблокированным. Физическое торможение не мгновенно: это обработка остановки,
а не планировщик обхода сингулярности или гарантия отсутствия выбега.

## Запись отставания servoJ

Телеметрия не меняет регулятор. По умолчанию `publish_diagnostics=false`.
После сборки образа и запуска backend в отдельном shell контейнера:

```bash
source /opt/ros/humble/setup.bash
source /ws/install/setup.bash
ros2 param set /ur_rtde_bridge publish_diagnostics true
ros2 run teleop_core rtde_diagnostics --output /tmp/rtde-trace-01.jsonl --duration 30
ros2 param set /ur_rtde_bridge publish_diagnostics false
```

Во время записи: несколько секунд покоя, плавный перенос при фиксированной
ориентации, пауза, небольшое вращение и отпускание clutch. Достаточно первого
обычного отказа; специально входить в сингулярность или усиливать параметры
для записи не нужно. Preview позволяет проверить запись, но не измерить отклик
робота: `command_sent=false` исключается из статистики исполнения.

После записи на хосте, из корня репозитория:

```bash
mkdir -p /tmp/ur3-traces
docker compose cp teleop:/tmp/rtde-trace-01.jsonl /tmp/ur3-traces/rtde-trace-01.jsonl
PYTHONPATH=ros/ros2_ws/src/teleop_core python3 -m teleop_core.rtde_diagnostics \
  --summarize /tmp/ur3-traces/rtde-trace-01.jsonl
```

Файл не перезаписывается: для следующего опыта выбирайте новое имя. Рекордер
только подписывается на ROS, не открывает RTDE Control и не отправляет команды.
`Ctrl+C` сохраняет уже полученные события. В конце выводится сводка.

`/teleop/rtde_diagnostics` содержит JSON одного цикла bridge:

- `q_actual`, `qd_actual`: обратная связь перед шагом исполнения;
- `q_cmd`: результат текущего успешного шага; только при `command_sent=true`
  это команда, успешно переданная через `servoJ`. В preview это расчёт без отправки;
- `q_last_sent`: последняя успешно отправленная команда, историческая после остановки;
- `q_reference_before`, `q_servo_hint`, `qd_servo`: интегратор и принятый вход Servo;
- режимы, `getSpeedScaling`, `getTargetSpeedFraction`, внутренние `getTargetQ/Qd` робота;
- `cycle_interval_s`, `timings_s`, возраст feedback/траектории, параметры gain/lookahead;
- `servo_status` с возрастом последнего статуса и статус bridge.

Поля снимка читаются в одном цикле, но не гарантируют один атомарный пакет RTDE.
`command_step_ms` включает проверки и вызов servoJ; это не чистая сетевая задержка.
Сводка показывает распределения отрыва команды и скоростей по суставам, интервалы
цикла, speed scaling и число NaN во входной траектории. Она не выдаёт отрыв позиции
за измеренную задержку и сама не определяет причину отказа. Устойчивая меньшая
actual-скорость при росте отрыва требует сопоставления с состоянием программы,
speed scaling и статусами Servo. Режимы/паузы анализируются по времени события.

Телеметрия передаётся через ограниченную очередь; `diagnostics_dropped` и
`sequence_gaps` позволяют заметить пропуски. Статистика относится только к
полученным отсчётам. JSONL также сохраняет исходную траекторию, Twist, active и
статусы как отдельные события с временем получения; NaN/Inf кодируются `null`
и отмечаются флагом `nonfinite` у траекторий.

## Первый запуск: без отправки движения

1. Собрать новый образ. Старый workshop-образ не содержит новых узлов/ur_rtde.
   В `.env` выбрать `TELEOP_IMAGE=ur3-vr-teleoperation:humble`.
2. Сохранить существующий ROBOT_IP в `.env`. Новые параметры можно добавить
   из раздела RTDE в `.env.example`. Значения по умолчанию уже есть в Compose.
3. Для первого запуска оставить:

   ```dotenv
   RTDE_ENABLE_MOTION=false
   RTDE_ENABLE_GRIPPER=false
   RTDE_FREQUENCY=125.0
   ```

4. Из корня репозитория:

   ```bash
   ./scripts/run.sh build
   ./scripts/run.sh rtde
   ./scripts/run.sh logs
   ```

5. В Unity открыть WorkshopScene. Найти объект с ControllerTwistPublisher
   (по GUID сцены это объект с Transform 320328463). Рядом уже добавлен
   **ControllerPosePublisher** с теми же rightController / robotBase.
   Включить **Pose Mode** в Inspector до Play. По умолчанию он выключен,
   чтобы не менять работу прежних режимов. Для APK сохранить выбор и пересобрать приложение.
6. Подключить Unity к Endpoint (ROS 2, IP компьютера, порт 10000).
   Отпустить Trigger после старта, затем нажать и двигать контроллер.

Preview создаёт только RTDEReceiveInterface: не загружает управляющий скрипт,
не создаёт RTDEControlInterface и не вызывает servoJ. MoveIt Servo при этом
работает и публикует рассчитанные суставные команды для просмотра. Мост в preview
проверяет один шаг от actual Q без накопления интегратора: робот намеренно не
движется, и накопление вызвало бы ложную ошибку отставания. Обратная связь читается
с реального робота. Мост захвата выключен независимо от ENABLE_GRIPPER старого режима.
Тесты с поддельным роботом описаны ниже; это не отдельный пользовательский симулятор.

Смотреть данные:

```bash
./scripts/run.sh shell
source /opt/ros/humble/setup.bash
source /ws/install/setup.bash
ros2 topic echo /teleop/tcp_actual
# Ctrl-C, затем другие точки наблюдения:
ros2 topic echo /vr/right_hand/pose
ros2 topic echo /teleop/target_pose
ros2 topic echo /teleop/rtde_status
ros2 topic echo /teleop/pose_status
ros2 topic echo /teleop/servo/twist
ros2 topic echo /teleop/servo/joint_trajectory
ros2 topic echo /teleop/servo/status
ros2 topic echo /teleop/tracking_status
```

## Координаты, опорная поза и вращение

### Разместить сцену перед собой в очках

В WorkshopScene под элементом подключения меню добавляется кнопка **Calibration**.
Нажать её, повернуться лицом к реальной установке и нажать **A** на правом
контроллере либо **Apply**. Виртуальное основание окажется перед пользователем
на расстоянии 1.5 м (поле `distanceToRobot` у `WorkshopViewCalibration`).
В режиме калибровки команды руки/Trigger и захвата приостановлены. **Cancel**
выходит без изменения размещения. После Apply нужно отпустить Trigger перед
следующим управлением. Для первой проверки использовать preview.

Меняется только горизонтальное положение и yaw XR Origin; стол, робот и их
взаимное положение остаются прежними, масштаб и высота не меняются. После Apply
автоматическая коррекция origin через XRStateManager приостановлена до следующего
запуска приложения, чтобы она не отменяла ручное размещение. Размещение действует
в текущей сессии; после recenter/tracking reset при необходимости повторить.

Это ручное совмещение вида с направлением взгляда, не измеренная калибровка
основания UR: оно не определяет реальные +X/+Y робота. Оси и
`RTDE_MAPPING_YAW_DEG` по-прежнему нужно проверить в preview. При наклонной
установке робота одной настройки yaw недостаточно.

Unity публикует позу руки в `vr_robot_base`: координаты относительно **фиксированного
основания визуального UR3**, преобразованные Unity ROSGeometry в FLU. ROS берёт
фактический TCP из RTDE, а не из модели Unity, и фиксирует две опорные позы при Trigger.
Относительное движение руки преобразуется в целевую позу TCP. Опорная поза робота
не обновляется за движущимся роботом. Отпускание и новое нажатие дают новую привязку.

Выходная цель и RTDE feedback используют frame `base` — основание реального UR.
`RTDE_MAPPING_YAW_DEG=180` задаёт обычный поворот между URDF base_link и UR base;
на конкретной сцене и установке направления обязательно проверить в preview.
Для другой калибровки доступен yaw в градусах. Произвольная полная extrinsic-калибровка
и компенсация изменения основания VR пока не реализованы. Старые покомпонентные
angularRosSigns и SPEEDL_LINEAR_* здесь **не применяются**.

Ориентация считается кватернионами: относительное вращение руки переводится
в оси робота и умножается на ориентацию TCP при привязке. Вектор вращения UR
получается только на границе RTDE. TCP — именно активный TCP контроллера;
нужно понимать, какой инструмент/TCP настроен на pendant, он может отличаться от tool0 Unity.

Смещение UTC-часов Quest относительно ROS измеряется обменом
`/teleop/clock_ping` → `/vr/clock_pong` (std_msgs/String с JSON) каждые 0.5 с.
Ответ содержит ID запроса, исходную ROS-метку, две UTC-метки Quest и ID сессии
приложения. ROS проверяет соответствие запросу и оценивает смещение по четырём
меткам. Требуются три замера; принимаются только обмены с полным временем до
100 мс. Из свежего окна 5 с выбирается замер с минимальным RTT. Это оценка,
зависящая от асимметрии задержек, а не точная синхронизация системных часов.

Проверяется возраст позы с учётом смещения, а порядок — по исходным меткам Quest.
Старые (более 1 с) и идущие назад метки отклоняются. Без свежих замеров времени
цели не публикуются. При потере синхронизации, смене сессии приложения или
скачке часов требуется восстановление обмена и отпускание Trigger.
Статус: `ros2 topic echo /teleop/clock_status`; пример:
`SYNCED client_minus_ros=+113.00ms rtt=25.00ms`. Сам топик позы сохраняет
исходную метку Quest: отрицательный raw age теперь сам по себе не означает отказ.
Нужны одновременно обновлённый ROS-образ и APK; старый APK не отвечает на ping.
Неизменный heartbeat без
новых поз не считается свежим вводом. Тайм-аут приёма позы и Trigger — 0.25 с.

## Включение движения после проверки цели

После проверки направлений и ориентации установить в `.env`:

```dotenv
RTDE_ENABLE_MOTION=true
# Только если нужен реальный захват:
RTDE_ENABLE_GRIPPER=true
```

Применить `./scripts/run.sh rtde`. Изменение .env не требует build.
Это создаст ControlInterface и загрузит его управляющий скрипт на робота.
Не оставлять другие источники команд движения (старый backend, программа политики,
другой RTDEControl/External Control) активными на этом роботе.
Требования remote control зависят от поколения контроллера и PolyScope.
Для CB3 UR3 начальная частота 125 Гц; e-Series может использовать 500 Гц,
но менять её следует после проверки модели и времени цикла.

## Регулятор позы и MoveIt Servo

`relative_pose_controller` по-прежнему фиксирует опоры руки/робота и выдаёт
абсолютную целевую позу. Между обновлениями цели регулятор 125 Гц удерживает
последнюю цель и каждый раз пересчитывает ошибку относительно actual TCP:

- `v = position_gain * (target.position - actual.position)`;
- угловая скорость — `rotation_gain` на кратчайший вектор ошибки вращения;
- нормы скоростей ограничены `RTDE_MAX_LINEAR_SPEED` и `RTDE_MAX_ANGULAR_SPEED`.

`RTDE_POSITION_GAIN` и `RTDE_ROTATION_GAIN` по умолчанию 2.0 1/с. Это коэффициенты
внешней обратной связи, отдельные от `RTDE_GAIN` внутреннего `servoJ`.
Цели, actual TCP и входной Twist выражены в `base`. Planning frame Servo —
`base_link`, совпадающий с основанием SRDF/KDL-цепи; Servo сам преобразует Twist
между этими системами. Servo получает реальные `/joint_states`,
модель UR3 и Twist, рассчитывает суставные положения/скорости и публикует
короткую `JointTrajectory` с одной точкой. Частота регулятора, Servo и RTDE
задаётся одним `RTDE_FREQUENCY` (по умолчанию 125; для этого UR3 launch — не выше 125).
Возможность выдерживать период 8 мс на установке необходимо измерить.

Суставные скорости берутся из `config/joint_limits.yaml` (1.0 рад/с для первых
трёх, 1.2 рад/с для запястья), ограниченные сверху пределами URDF.
Те же пределы получает мост. Он упорядочивает суставы по именам, проверяет
числа и положения, интегрирует выходные скорости Servo:
`q_cmd[k+1] = q_cmd[k] + qd_servo[k] / frequency`. Позиции из Servo остаются
дополнительной проверкой входной команды. Мост ограничивает общий масштаб каждого отправляемого шага
`q_cmd - q_previous` так, чтобы каждый сустав укладывался в `max_velocity / frequency`.
Первый шаг начинается с actual Q; отпускание сбрасывает опору команды.
Нулевые команды после повторного включения удерживают новую actual Q, а не
старую позицию, которую Servo мог сохранить до отпускания. Непрерывный
`wrist_3` разворачивается в ближайший к actual угол без скачка на полный оборот.
Это ограничения команд; фактическая динамика зависит от контроллера UR.

Непрерывная опора нужна для исполнения через позиционный `servoJ`: если каждый
раз передавать только `actual Q + qd * 0.008`, контроллер с конечным временем
отклика не успевает выполнить шаг, а следующая цель снова строится от actual.
Это снижает фактическую скорость. Интегратор сохраняет опору между циклами;
при отпускании, тайм-ауте или ошибке она сбрасывается. При отставании actual
больше `RTDE_MAX_JOINT_TRACKING_ERROR` интегратор останавливается, а не продолжает
накапливать команду. Лимиты скорости и параметры gain/lookahead этим исправлением
не увеличиваются.

`RTDE_LOWER_SINGULARITY_THRESHOLD=17` начинает замедление при движении к
сингулярности, `RTDE_HARD_STOP_SINGULARITY_THRESHOLD=30` останавливает его.
Для выхода учитывается `leaving_singularity_threshold_multiplier=2`.
Эти параметры масштабируют скорость по обусловленности якобиана, а не включают DLS.

### Модель, TCP и будущая калибровка

Пока используется официальный nominal UR3 из `ur_description`. Одно и то же
описание получают Servo и `robot_state_publisher`. Позже файл заводской
калибровки можно передать параметром launch `kinematics_params_file` или
`RTDE_KINEMATICS_PARAMS_FILE` — путь должен существовать **в контейнере**.
Например, файл внутри `teleop_core/config/` попадает в образ при сборке; для
внешнего файла добавьте read-only volume в локальный Compose override.

Для активного TCP к `tool0` добавлен фиксированный link `teleop_tcp`; он же
является концом кинематической цепи. Настройки:

```dotenv
RTDE_TCP_XYZ=[0.0, 0.0, 0.0]
RTDE_TCP_RPY=[0.0, 0.0, 0.0]
```

XYZ — метры; RPY — фиксированные углы roll/pitch/yaw в радианах, **не** UR rotation
vector. Нули соответствуют TCP `tool0`. Если на pendant настроен иной активный TCP,
нужно задать такое же смещение здесь до движения. Автоматического чтения/изменения
TCP и проверки совпадения FK с actual TCP пока нет. После загрузки калибровки
сверить FK `base → teleop_tcp` и RTDE TCP в нескольких конфигурациях.

### Остановки

- Относительная цель ограничена `RTDE_MAX_DISPLACEMENT` и `RTDE_MAX_ROTATION`.
- Потеря позы/heartbeat, actual feedback или команд Servo блокирует движение.
- `RTDE_TRAJECTORY_TIMEOUT=0.1` ограничивает ожидание очередной команды Servo;
  `RTDE_COMMAND_TIMEOUT=0.25` — heartbeat; `RTDE_FEEDBACK_TIMEOUT=0.25` — feedback.
- Humble Servo публикует stamp=0 («сразу»); для таких команд используется время
  приёма. Для ненулевой метки дополнительно проверяются возраст и порядок.
  Подписка глубиной 1 хранит последнюю команду, траектории не накапливаются.
- Расхождение командного/целевого положения сустава с actual больше
  `RTDE_MAX_JOINT_TRACKING_ERROR=0.15` рад вызывает остановку.
- Не normal safety mode / не running robot mode, пропуск цикла >4 периодов,
  неверная траектория или отказ `servoJ` вызывают остановку.
- После ошибки требуется отпускание и новое нажатие Trigger. Ошибка RTDE или
  исполнения команды завершает worker; для восстановления нужен перезапуск режима.
- При выключенном управлении регулятор отправляет нулевой Twist и false
  на `/teleop/servo/active`; мост вызывает `servoStop` из своего рабочего потока.

Прежний `RTDE_POSE_CHECK_MODE` больше не используется: удалённого
`isPoseWithinSafetyLimits` и `servoL` в этой цепочке нет. Старую переменную
можно удалить из локального `.env`.

Это программные ограничения прототипа. Collision checking в новом конфиге
выключен до настройки геометрии установки. Ограничения ускорения из YAML сами
по себе не гарантируют ограничение ускорения/jerk в выбранном фильтре Servo;
отдельного ограничителя ускорения в мосте нет. Встроенные защиты UR сохраняются.

## Реализация

- `relative_pose_controller.py` — относительная привязка, свежесть ввода и цель.
- `pose_tracking_controller.py` — обратная связь по позе, Twist и разрешение движения.
- `joint_control.py` — математика регулятора и проверка/ограничение суставных команд.
- `ur3_rtde_servo.yaml` — отдельная конфигурация Servo реального режима.
- `ur_rtde_bridge.py` — один поток владеет Receive/Control; публикует actual Q/Qd/TCP,
  принимает последнюю суставную команду, интегрирует ограниченные скорости и исполняет `servoJ`.
- `rtde_real.launch.py` — общая модель, настройки частоты, все узлы цепочки,
  опциональный Robotiq. UR Driver и старый speedl-мост не запускаются.

Переход назад: отпустить Trigger, выключить Pose Mode в Unity, затем
`./scripts/run.sh servo` или `./scripts/run.sh up`.

## Защиты и столкновения

В реальном режиме включены программные ограничения скорости TCP и суставов,
суставных положений, обработка сингулярностей Servo, контроль свежести входа,
heartbeat и RTDE feedback, контроль отставания командной позы суставов и пропуска
периода. Это не сертифицированная система безопасности; штатные защиты UR
настраиваются на контроллере отдельно.

**Проверки столкновений сейчас выключены**: `check_collisions: false` в
`ur3_rtde_servo.yaml` (и в старом симуляционном конфиге). Поэтому нет защиты
Servo от самостолкновений и контакта с полом/столом. Стол и пол Unity автоматически
не добавляются в MoveIt planning scene. Для включения нужны проверенная collision
геометрия робота и захвата, объекты пола/стола с измеренными координатами,
настройка SRDF/разрешённых пар контактов и проверка остановок с учётом опережения
интегрированной команды. Один параметр `check_collisions: true` сам по себе не
создаёт эту геометрию. Фиксированный `teleop_tcp` задаёт только систему координат,
а не collision-объём захвата или удерживаемого предмета.

## Аналоговый захват и фиксация A

В `WorkshopScene` управление Robotiq использует аналоговый **Grip правого
контроллера** (боковой курок), независимо от Trigger перемещения руки:

- степень нажатия Grip `0..1` задаёт положение пальцев от открытого до закрытого;
- первое нажатие **A** фиксирует заданное в этот момент положение;
- после фиксации Grip можно отпустить, положение сохраняется;
- повторное A возвращает управление Grip: если Grip отпущен — захват открывается,
  если нажат — следует текущему значению;
- при калибровке вида A подтверждает калибровку; фиксация захвата заблокирована.
  После выхода требуется отпустить A перед новым переключением;
- потеря tracking не отправляет открытие и не переключает фиксацию.

Это **команда положения, а не регулирование усилия**. Положение реального захвата
при контакте с объектом может отличаться; обратная связь пальцев в фиксации не
используется. Усилие задаётся отдельным `GRIPPER_FORCE`, скорость движения пальцев —
параметром ROS-моста `speed`.

Топик остаётся `/team_1/gripper_command`, тип `std_msgs/String`: Unity отправляет
числовую строку `0.000..1.000`, ROS переводит её в диапазон Robotiq `0..255`.
Старые `open`/`close` и команды `0..255` поддерживаются. Примеры:
`"0.000" → 0`, `"0.500" → 128`, `"1.000" → 255` при стандартных конечных положениях.
Unity публикует изменения до 10 Гц; мост отправляет последнюю команду не чаще
одного раза за `min_command_interval_sec` (по умолчанию 0.2 с). Старые промежуточные
положения в очередь движения не накапливаются. Виртуальное прикрепление объекта
тоже учитывает фиксацию A, но использует условный порог сжатия.

Для применения нужны новая сборка ROS-образа и пересобранное приложение Unity/APK.
До подключения к реальному захвату можно проверить значения через:

```bash
ros2 topic echo /team_1/gripper_command
```

## Проверки без оборудования

```bash
PYTHONPATH=ros/ros2_ws/src/teleop_core python3 -m unittest discover -s tests -v
# В окружении с ROS, без подключения к реальному роботу:
python3 tests/rtde_ros_smoke.py -v
```

Второй тест запускает настоящий MoveIt Servo с nominal UR3 и ненулевым смещением
TCP, подменяя только RTDE Receive/Control. Проверяет сквозную цепочку с вводом
30 Гц, движение по рассчитанным суставным положениям, preview без ControlInterface,
ограничение каждого суставного шага, остановки при потере VR/Servo/feedback
и запрет возобновления при удерживаемом Trigger. Поддельный робот имеет конечное время отклика на позиционные команды, чтобы
выявлять потерю скорости при привязке каждого шага к actual Q. Это приближение
не подтверждает сетевые задержки и динамику реального UR3.
