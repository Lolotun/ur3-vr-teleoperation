# Почему робот останавливался и что изменили в управлении

Разбор записи `rtde-trace-01.jsonl` и реализации anti-windup от 6 ноября 2026 года.
После применения изменений оператор отметил заметное улучшение управления.
Количественное сравнение с новой записью пока не выполнено.

## 1. Какие команды проходят по цепочке

```text
Quest: положение руки и clutch
  → relative_pose_controller: целевая поза TCP, 30 Гц
  → pose_tracking_controller: ошибка относительно actual TCP → Twist, 125 Гц
  → MoveIt Servo: суставные позиции-подсказки и скорости, 125 Гц
  → ur_rtde_bridge: интегрирование скоростей → позиционная команда servoJ
  → UR3

UR3 → RTDE Receive → actual TCP, фактические углы и скорости суставов
```

Обозначения:

| Поле | Значение |
|---|---|
| `q_actual` | Измеренные углы с контроллера робота |
| `qd_actual` | Измеренные суставные скорости |
| `q_servo_hint` | Позиционная подсказка из MoveIt Servo, а не окончательная команда роботу |
| `qd_servo` | Суставные скорости из принятой траектории Servo |
| `q_reference_before` | Накопленная позиционная команда перед текущим шагом |
| `q_cmd` | Результат текущего шага; при `command_sent=true` успешно передан через `servoJ` |
| `q_last_sent` | Последняя успешно отправленная команда; после остановки это историческое значение |
| `/teleop/target_pose` | Цель TCP оператора; это другая величина, чем суставная `q_cmd` |

Все суставные положения в записи — радианы, скорости — рад/с.
`command_sent=true` не доказывает, что робот уже достиг этой позиции.

## 2. Что происходило раньше

Вместо прямой отправки позиционной подсказки Servo bridge интегрирует его скорости:

```text
dt = 1 / 125 = 0.008 с
q_cmd_next = q_cmd + qd_servo × dt
```

Это позволяет сохранять непрерывную команду при отставании позиционного
исполнения. Но без ограничения накопления команда может убегать вперёд.

Пример одного сустава:

```text
actual = 0.000 рад
команда = 0.080 рад
новая скорость = 1.000 рад/с

старый шаг: 0.080 + 1.000 × 0.008 = 0.088 рад
```

Если actual растёт медленнее команды, разрыв увеличивается. Раньше очередной
шаг отклонялся, когда превышал аварийный предел `0.15 рад` — примерно `8.6°`.
Оператору приходилось отпускать clutch и начинать заново.

У этой проблемы было и второе проявление: при `qd_servo=0` накопленная команда
не исчезает. Позиционный `servoJ` может продолжать вести робот к ней.

```text
actual wrist_2 = 5°
накопленная команда wrist_2 = 1°
Servo перестал добавлять скорость
bridge продолжает отправлять позицию 1°
```

Следовательно, прекращение интеграции само по себе не означает остановку робота.

## 3. Что показала первая запись

Исходный файл: `tmp/rtde-trace-01.jsonl` — локальная диагностическая запись,
не включённая в коммит исходного кода.
Время ниже отсчитывается от первого полученного диагностического отсчёта,
а не от запуска программы. Запись началась, когда робот уже двигался.

| Время | Причина отказа | Разрыв команды `wrist_1` |
|---|---|---:|
| 0.20 с | Суставная команда превысила порог | +0.151516 рад |
| 5.22 с | Суставная команда превысила порог | −0.150952 рад |
| 7.91 с | Суставная команда превысила порог | −0.151969 рад |

Во втором эпизоде статус Servo был `0`: для этой остановки не требовалась
сингулярность. В последние примерно 80 мс перед ним Servo требовал от `wrist_1`
скорость `−1.2 рад/с`, а actual в приведённых отсчётах составляла примерно
`−0.57…−0.88 рад/с`. Разрыв достиг порога.

Другие наблюдения:

- NaN в траекториях в этой записи отсутствовали.
- Перед отказами цикл bridge оставался около `8 мс`.
- Максимальный интервал `66.6 мс` появился после отклонения команды:
  длительный шаг включал обработку остановки. Он не предшествовал первому отказу.
- Обычный шаг проверки и отправки команды занимал около `0.03 мс`.
  Это длительность вызова на ПК, а не время достижения позиции роботом.
- `getSpeedScaling=1.0` и `getTargetSpeedFraction=0.78` были постоянны.
  Меняющегося ограничения по первому полю не наблюдалось; влияние заданной
  доли скорости `0.78` отдельно не измерялось.
- Режимы программы, робота и безопасности в диагностических отсчётах
  оставались соответственно `2`, `7`, `1`.

### Оценка запаздывания отклика

На непрерывных участках отправки команд сравнили actual с командой, сдвинутой
назад во времени. Для оценки использовали отсчёты спустя не менее `0.3 с` от
начала участка, со статусом Servo `0` и модулем actual-скорости больше `0.1 рад/с`.
Перебирали сдвиг `0…300 мс` с шагом `1 мс`, минимизируя среднеквадратичную ошибку
положения. Лучшими оказались сдвиги:

| Сустав | Сдвиг кривой команды | RMSE после сдвига |
|---|---:|---:|
| elbow | 146 мс | 0.0021 рад |
| wrist_1 | 145 мс | 0.0038 рад |
| wrist_2 | 143 мс | 0.0029 рад |

Это приближённое совмещение кривых в данном опыте, не универсальная постоянная
задержки и не измерение сетевой задержки. Gain был `300`, lookahead — `0.1 с`.
Из одной записи нельзя отделить влияние этих настроек от остальных свойств
исполнения. Чтение полей RTDE в цикле также не гарантирует один атомарный пакет.

Для понимания масштаба: при `1.2 рад/с` и запаздывании порядка `0.145 с`
характерный разрыв составляет `1.2 × 0.145 ≈ 0.174 рад` — больше нашей защиты
`0.15 рад`. Это оценка, а не точная модель переходного процесса.

### Эпизод возле сингулярности

Около `12.684 с` появился статус Servo `2`. В этот момент:

```text
wrist_2 actual ≈ 4.515°
wrist_2 команда ≈ 2.795°
```

Через примерно `120 мс` actual приблизился до `3.413°`. Bridge всё ещё отправлял
команды. На этом участке выходные скорости Servo тоже не стали мгновенно
нулевыми: например, скорость-команда `wrist_1` уже меняла направление, пока
actual продолжал прежнее движение. Поэтому этот эпизод нельзя описать только
как «нулевая скорость и одна сохранённая позиция». Нужна отдельная реакция
исполнителя на защитный статус.

## 4. Новое ограничение накопления: anti-windup

Ограничиваем рост отрыва до достижения аварийной границы.

| Параметр | По умолчанию | Назначение |
|---|---:|---|
| `RTDE_LEAD_SOFT_START` | 0.06 рад ≈ 3.44° | Начало плавного ограничения |
| `RTDE_LEAD_SOFT_LIMIT` | 0.10 рад ≈ 5.73° | Рабочая граница роста отрыва |
| `RTDE_MAX_JOINT_TRACKING_ERROR` | 0.15 рад ≈ 8.59° | Независимая аварийная граница |

Обязательно: `0 < soft_start < soft_limit < hard_limit`.
Локальный `.env` автоматически не переписывался; новые значения по умолчанию
передаются через Compose, entrypoint и launch после пересборки образа.

Для каждого сустава рассматриваем текущий отрыв и требуемое приращение:

```text
e = q_reference_before − q_actual
d = qd_servo × dt
```

Если приращение направлено дальше от actual, вычисляем плавный коэффициент:

```text
x = clamp((soft_limit − abs(e)) / (soft_limit − soft_start), 0, 1)
alpha_joint = x² × (3 − 2x)
```

Берём минимальный допустимый коэффициент по суставам и дополнительно проверяем,
что текущий шаг не перескочит рабочую границу:

```text
q_cmd_next = q_reference_before + alpha × qd_servo × dt
```

Один общий `alpha` сохраняет соотношение компонентов приращения суставов.
Это не гарантия абсолютно той же декартовой траектории: фактическая конфигурация
и внешний регулятор продолжают изменяться.

Примеры при скорости `1 рад/с`, шаге `8 мс` и отсутствии ограничений других суставов:

| Отрыв перед шагом | Коэффициент | Новое приращение вместо 0.008 рад |
|---:|---:|---:|
| 0.040 рад | 1.00000 | 0.00800 рад |
| 0.070 рад | 0.84375 | 0.00675 рад |
| 0.080 рад | 0.50000 | 0.00400 рад |
| 0.090 рад | 0.15625 | 0.00125 рад |
| 0.100 рад | 0.00000 | 0 рад при дальнейшем росте |

Если робот догоняет команду, отрыв уменьшается и коэффициент снова растёт.
Фиксированную позицию не обрезаем скачком к actual: ограничиваем именно новое
приращение. При неподвижном actual команда приближается к рабочей границе,
а не накапливается бесконечно.

### Смена направления

```text
actual = 0.000 рад
команда = 0.090 рад
запрос скорости = −0.500 рад/с

новая команда = 0.090 − 0.500 × 0.008 = 0.086 рад
```

Приращение сокращает отрыв, поэтому этот сустав не требует замедления.
Однако общий коэффициент может ограничиваться другим суставом, если тот
одновременно продолжает уходить от своего actual.

### Почему аварийная защита осталась

Actual может сместиться независимо от интегратора. Например, команда осталась
`0.10 рад`, а actual внезапно стал `−0.08 рад`: разрыв уже `0.18 рад`.
Anti-windup не должен скрывать такое событие переносом команды.
Аварийная проверка продолжает останавливать исполнение.

Если внешний сдвиг оставил отрыв между рабочим и аварийным пределами,
разрешается уменьшение отрыва, но запрещается дальнейшее его увеличение.

## 5. Новая обработка остановок Servo

Bridge теперь отдельно обрабатывает:

| Статус Servo | Причина |
|---:|---|
| 2 | Остановка возле сингулярности |
| 4 | Остановка из-за коллизии |
| 5 | Ограничение положения сустава |

После получения такого статуса:

1. Блокируется принятие новых команд для исполнения.
2. В ближайшем цикле RTDE сбрасывается интегратор и вызывается `servoStop`,
   если сессия уже отправляла команду.
3. Публикуется `SERVO_HALT_RELEASE_TO_REARM: status=...`.
4. Чтение actual TCP и суставов продолжается.
5. `relative_pose_controller` сбрасывает прежнюю привязку руки и цели TCP.

Для повторного включения нужны:

- физическое отпускание clutch: `/vr/right_hand/active=false` после события;
- свежий статус Servo без остановочного кода;
- новое включение управления. Первое обновление цели привязывается к текущим
  руке и actual TCP.

Автоматическое `/teleop/servo/active=false` не считается отпусканием оператора.
Статусы замедления `1`, `3`, `6` сами по себе не вызывают эту защёлку.

Пример: оператор успел увести цель TCP далеко вперёд, затем Servo остановился.
Раньше после восстановления мог снова появиться большой запрос к старой цели.
Теперь после отпускания и нового нажатия начальная цель совпадает с текущим
TCP. Для нового движения оператор заново перемещает руку.

Обычный нулевой Twist без защитного статуса остаётся удержанием позиции.

## 6. Что изменили в обработке остальных ошибок

| Событие | Реакция | Как восстановить |
|---|---|---|
| Отклонена суставная команда, включая превышение аварийного отрыва | Остановить сессию, сбросить интегратор, сохранить feedback | Отпустить и снова нажать clutch после устранения причины |
| Защитный статус Servo 2/4/5 | Остановка, сброс интегратора и VR-привязки, сохранить feedback | Физический release, свежий неостанавливающий статус, новое нажатие |
| `servoJ` вернул отказ / RuntimeError в шаге исполнения | Сохранить feedback, запретить новые команды | Разобраться с причиной и перезапустить backend |
| Потеря Receive / устаревшая обратная связь | `FAULT`, завершение рабочего потока | Восстановить связь и перезапустить backend |

После отклонения команды или отказа `servoJ` обратная связь продолжает работать,
если соединение Receive остаётся исправным.
Для отказа `servoJ` автоматического перезапуска программы робота нет.

## 7. Как проверить результат следующей записью

Используем тот же gain, lookahead, долю скорости контроллера и похожие движения.
Иначе будет сложно отделить эффект anti-windup от других изменений.
Специально добиваться сингулярности для сравнения не требуется.

В контейнере с запущенным backend:

```bash
source /opt/ros/humble/setup.bash
source /ws/install/setup.bash
ros2 param set /ur_rtde_bridge publish_diagnostics true
ros2 run teleop_core rtde_diagnostics \
  --output /tmp/rtde-trace-02.jsonl --duration 30
ros2 param set /ur_rtde_bridge publish_diagnostics false
```

Сценарий: несколько секунд покоя, плавный перенос без вращения, пауза,
небольшое вращение, отпускание clutch. Достаточно одного обычного защитного
события, если оно возникнет. Имя файла должно быть новым — рекордер не перезаписывает.

На хосте, из корня репозитория:

```bash
mkdir -p tmp
docker compose cp teleop:/tmp/rtde-trace-02.jsonl tmp/rtde-trace-02.jsonl
PYTHONPATH=ros/ros2_ws/src/teleop_core python3 -m teleop_core.rtde_diagnostics \
  --summarize tmp/rtde-trace-02.jsonl
```

При просмотре JSONL выбираем только события `/teleop/rtde_diagnostics` для
сопоставления команды и actual одного цикла. Скорость из отдельного события
траектории может относиться к другому моменту получения.

| Что смотреть | Что ожидаем / как интерпретировать |
|---|---|
| `abs(q_cmd − q_actual)` при `command_sent=true` | Рост от интегратора ограничивается около рабочего предела, без регулярных ударов в 0.15 рад |
| `anti_windup_scale` | Меньше 1 при ограничении; это уменьшение приращения команды, а не аппаратный speed scaling |
| `anti_windup_limited_samples` в сводке | Сколько отправленных шагов были ограничены; долю считайте относительно `sent_samples` |
| Частые значения коэффициента около 0 | Робот не успевает за запрашиваемым движением; полезно разбирать скорости и настройки исполнения |
| Переход Servo к 2/4/5 | Команды прекращаются после реакции bridge, status меняется на `SERVO_HALT_RELEASE_TO_REARM` |
| `q_cmd=null`, но `q_last_sent` не пуст | В текущем цикле новой команды нет; историческое поле не означает продолжение отправки |
| После нового нажатия clutch | Цель привязана к текущему TCP, старой далёкой цели нет |
| `diagnostics_dropped_in_bridge` и `sequence_gaps` | Нужны для оценки полноты записи; в первом опыте оба были 0 |

Для оценки движения после остановки смотрим actual с учётом времени получения
статуса и последующего торможения. Нельзя требовать мгновенного нулевого actual
в том же отсчёте, где появился статус.

## 8. Проверки и границы результата

При реализации прошли 57 модульных и 7 интеграционных тестов. Среди сценариев:

- actual не двигается: команда ограничивается без накопления до аварийного порога;
- медленно следующий робот и смена направления;
- сохранение общей пропорции приращений суставов;
- независимое смещение actual: аварийная защита всё ещё срабатывает;
- остановочный статус Servo: интегратор сброшен, feedback сохранён;
- автоматический active=false не разрешает повторный запуск при удерживаемом clutch;
- после физического release старая цель VR не восстанавливается;
- отказ servoJ по-прежнему не снимается нажатием clutch.

Эти тесты используют поддельный RTDE; они не измеряют тормозной путь реального UR3.
Изменения не устраняют само запаздывание servoJ, не выбирают другую конфигурацию
запястья и не планируют обход сингулярности. Ошибка численного решателя с NaN —
отдельная задача; anti-windup не превращает NaN в допустимую команду.

Разница часов Quest и ROS (`client_minus_ros`) также отличается от измеренного
отставания исполнения. В первой записи не обнаружено признаков, что именно
потеря синхронизации вызвала три рассмотренных отказа.
